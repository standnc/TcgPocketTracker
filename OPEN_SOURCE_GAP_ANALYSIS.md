# Análisis de carencias para publicación open source

Auditoría independiente realizada en la rama `open-source-prep`, sobre el estado del código en `main` a fecha 2026-08-28. Toda verificación se ejecutó con `PTCGP_DATA_DIR` apuntando a un directorio temporal; en ningún momento se abrió, migró ni modificó la base de datos real de Pedro (`~/.local/share/ptcgp-mcp/`).

## Lo verificado como funcional hoy

| Área                    | Evidencia concreta                                                                                                                                                                                                                                                                                                                                            |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Arranque MCP/stdio      | `npm run smoke` levanta el servidor compilado contra un `PTCGP_DATA_DIR` temporal y lista exactamente 17 tools (ver tabla más abajo). `PRAGMA quick_check` devuelve `ok` sobre esa base temporal.                                                                                                                                                             |
| SQLite                  | `better-sqlite3` con `journal_mode=WAL`, `foreign_keys=ON`, `busy_timeout=5000`. Migraciones versionadas en `schema_migrations`, forward-only, idempotentes (`src/db.ts`). Un test crea una base con el esquema antiguo y comprueba que la migración de columnas de combate se aplica y se registra una sola vez.                                             |
| Escrituras de colección | `ptcgp_set_card_quantity`, `ptcgp_bulk_update_collection` y `ptcgp_mark_range` usan siempre sentencias preparadas con parámetros (posicionales o `@nombre`); no se concatena SQL en ningún punto revisado. `mode=add` fija el suelo en 0 tanto en el `INSERT` como en el `ON CONFLICT`. Las operaciones masivas corren dentro de una transacción.             |
| Rondas de captura       | `ptcgp_round_finalize` exige `confirm=true`, recalcula `total_catálogo − huecos` y lo compara con `expected_owned_unique`; si no cuadra, no toca `owned` y devuelve el desfase exacto. ## Parcial, no probado, o documentado de forma optimista

| Área                        | Estado                                                                                                       | Motivo                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| --------------------------- | ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| HEIC/HEIF                   | **No soportado en este entorno**, pese a estar en la whitelist de extensiones (`src/screenshot-analyzer.ts`) | Comprobación directa: `sharp.format.heif.input.fileSuffix` solo incluye `.avif`; no hay `id: "heic"` ni sufijo `.heic` en el build de libvips instalado. Una captura `.heic` real (típica de iPhone) probablemente falla o se decodifica mal. Hay que verificarlo con una imagen real de prueba (no de Pedro) o documentar el requisito de una build de Sharp con soporte HEIC completo, y mientras tanto avisar de esta limitación en el README en vez de prometerla. |
| Detección de huecos por OCR | Parcial                                                                                                      | El heurístico (umbral de blancos, densidad de bordes, votos OCR con 3 umbrales) es sofisticado pero no tiene corpus público representativo; el test público solo prueba normalización de imágenes sintéticas, no precisión de detección real. El flujo obliga a revisión humana antes de `finalize`, lo cual mitiga el riesgo, pero no hay medida de precisión/recall documentada.                                                                                     |
| Cobertura de capturas       | Parcial                                                                                                      | `finalize` valida el recuento total, no que las rutas de imagen cubran realmente desde la primera hasta la última carta de la expansión. Un usuario podría, en teoría, saltarse un tramo intermedio si los conteos globales coinciden por casualidad.                                                                                                                                                                                                                  |
| Sincronización de catálogo  | Frágil, sin red de seguridad                                                                                 | `src/sync.ts` descarga JSON crudo desde `raw.githubusercontent.com/chase-mew/pokemon-tcg-pocket-cards` sin fijar un commit/tag concreto y sin validar la forma de la respuesta con Zod. Un cambio de esquema upstream rompería el sync de forma silenciosa o con un error poco claro.                                                                                                                                                                                  |
| Mazos meta / decklists      | Frágil                                                                                                       | `src/limitless.ts` extrae datos de Limitless TCG mediante scraping HTML por expresiones regulares — no hay API oficial. Tiene reintentos con backoff exponencial y timeout de 15s, pero cero tests de contrato o fixtures HTML grabadas. Un cambio de maquetación en Limitless rompe el parser sin aviso más allá de "0 cartas detectadas". No se ha revisado si el scraping respeta los términos de uso del sitio.                                                    |
| Enriquecimiento TCGdex      | Parcial                                                                                                      | Usa la API oficial de TCGdex (más estable que el scraping), con concurrencia fija (15 para catálogo, 4 para Limitless) pero sin política de rate-limit configurable ni documentada.                                                                                                                                                                                                                                                                                    |
| Backups                     | Inexistente como funcionalidad                                                                               | No hay tool MCP de backup/restore, ni copia automática antes de aplicar una migración. El usuario depende de backups manuales fuera del proyecto (que sí existen en `~/.local/share/ptcgp-mcp/backups/` en la instalación real de Pedro, pero eso es un hábito externo, no una garantía del software).                                                                                                                                                                 |
| Logging                     | Presente pero mínimo                                                                                         | `src/logger.ts` (Pino a stderr) solo se invoca en `index.ts` para el arranque y errores fatales; ninguna tool registra logs operativos. Esto significa que el riesgo de fuga de datos sensibles en logs es bajo hoy, pero también que no existe todavía una política de redacción real que probar — es una promesa de diseño, no una mitigación implementada.                                                                                                          |
| CLI y otros transportes     | Inexistente                                                                                                  | Solo hay transporte stdio. No hay CLI para uso humano directo ni transporte Streamable HTTP.                                                                                                                                                                                                                                                                                                                                                                           |

## Riesgos de privacidad y del repositorio

- `git ls-files` no muestra ninguna base de datos, backup, captura real, log, cookie ni fichero `.env` rastreado. Solo hay placeholders intencionados: `.env.example` y `screenshots/{inbox,processed}/.gitkeep`.
- Las capturas reales de la colección de Pedro existen físicamente en `screenshots/processed/` en el checkout local, pero `.gitignore` las excluye correctamente (`screenshots/**` con excepciones solo para los `.gitkeep`); no están y no han estado nunca en el historial de commits de este checkout.
- La base de datos real (`~/.local/share/ptcgp-mcp/collection.db` + `-wal`/`-shm` + carpeta `backups/`) vive fuera del repositorio y no fue abierta para escritura durante esta auditoría.
- No se encontraron credenciales, tokens ni cookies en el árbol de código fuente rastreado. Esto no sustituye un escaneo de secretos sobre el historial completo antes de hacer público un remoto — este repositorio solo tiene 4 commits locales hasta ahora y ningún remoto configurado, así que ese escaneo sigue siendo trivial de hacer antes del paso 6 del roadmap.
- **Escaneo de secretos del historial completo (`git log --all -p`) ejecutado el 2026-08-28**: sin patrones de credenciales, tokens ni claves reales. Único hallazgo: los 4 commits existentes llevan como autor `standnc <standnc@proton.me>` — una dirección de correo real que quedaría expuesta permanentemente en el historial si el repositorio se hace público. Antes de la fase 6 (GitHub público), decidir si ese autor/email es aceptable para publicación o si conviene reescribir la identidad de los commits.
- **Revisión de fuentes externas ejecutada el 2026-08-28**:
  - `raw.githubusercontent.com/chase-mew/pokemon-tcg-pocket-cards` (`data/v4/...`, sin pin de commit/tag, sigue la rama `main`): el propio repositorio documenta que los datasets v1–v4 se mantienen bajo licencia MIT (permisiva, con atribución), mientras que v5 en adelante pasa a AGPL-3.0-or-later. El código del proyecto apunta explícitamente a la carpeta `v4`, así que hoy cae bajo MIT — pero al no fijar un commit, un cambio futuro de esa política de carpetas rompería el supuesto sin aviso. El propio repositorio aclara que las imágenes, nombres y logos de las cartas siguen siendo propiedad de Nintendo/Creatures/GAME FREAK/DeNA — la licencia MIT cubre el dataset, no la propiedad intelectual de Pokémon, lo cual es coherente con la regla ya existente de no redistribuir imágenes de cartas.
  - TCGdex (`api.tcgdex.net`): su web se describe como "freely available and open source", pero no expone en su página principal límites de rate ni una licencia de datos explícita. Queda pendiente revisar su repositorio (`tcgdex/cards-database`) directamente antes de una publicación pública.
  - Limitless TCG (`play.limitlesstcg.com`, `pocket.limitlesstcg.com`): no existe una página `/terms` accesible (404). `pocket.limitlesstcg.com/robots.txt` permite explícitamente el rastreo (`Disallow:` vacío); `play.limitlesstcg.com/robots.txt` no existe (404), ni prohíbe ni autoriza explícitamente. No hay evidencia de que el scraping esté técnicamente bloqueado, pero tampoco hay una licencia o ToS que lo autorice formalmente — sigue siendo el riesgo legal/estabilidad más alto de las tres fuentes y debería tratarse como no resuelto antes de publicar.
- **HEIC/HEIF confirmado como no soportado** (no solo "sin verificar"): `sharp.format.heif.input.fileSuffix` en el build instalado solo incluye `.avif`; no existe un `id: "heic"` independiente. La whitelist de `src/screenshot-analyzer.ts` debería dejar de prometer `.heic`/`.heif` en el README hasta instalar/compilar una build de Sharp con soporte HEIC completo (libheif con codec HEIC, no solo AVIF).

## Valoración técnica razonada

| Elección                | Postura                                       | Problema que resuelve / coste / prioridad                                                                                                                                                                                                                  |
| ----------------------- | --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| TypeScript estricto     | Mantener                                      | Ya está activo (`strict: true`) y sin errores. Coste cero, valor alto: mantenerlo es la base para extraer casos de uso con seguridad de tipos.                                                                                                             |
| Node.js LTS (22/24)     | Mantener                                      | `engines` y CI ya cubren ambas líneas soportadas; `better-sqlite3` es nativo, así que cualquier cambio de runtime exige `npm ci` limpio. Prioridad alta, coste bajo.                                                                                       |
| SDK oficial de MCP      | Mantener                                      | Ya en uso, sin acoplamiento a un proveedor de modelo. Coste bajo, valor alto: es literalmente el objetivo del proyecto.                                                                                                                                    |
| Zod                     | Extender, no sustituir                        | Ya valida `PTCGP_DATA_DIR`/`PTCGP_LOG_LEVEL`, inputs de cada tool y las respuestas de red consumidas en `sync.ts`/`limitless.ts`. Mantener esquemas mínimos y explícitos para que cambios upstream fallen de forma clara.                                  |
| Migraciones versionadas | Base implementada, recuperación por ampliar   | El ledger `schema_migrations` evita drift silencioso y `VACUUM INTO` crea un backup consistente antes de migrar una base con datos; la prueba de recuperación usa una base temporal. Falta política de retención y un flujo de restauración para usuarios. |
| Vitest vs `node:test`   | No cambiar todavía                            | El runner nativo de Node cubre bien los 34 tests actuales. Migrar a Vitest solo se justifica si aparece necesidad real de mocking avanzado, fixtures HTTP o cobertura; hacerlo ahora sería coste sin beneficio claro.                                      |
| ESLint + Prettier       | Base ya implementada                          | Ya integrados y en verde. Ajustar reglas solo en cambios puntuales futuros, no en esta fase.                                                                                                                                                               |
| Logging estructurado    | Base ya implementada, incompleta en cobertura | Pino a stderr es correcto arquitectónicamente, pero casi no se usa todavía. Antes de operar en red (fase 4+) hace falta una política de redacción explícita y logging real en las tools, no solo en el arranque.                                           |
| Build reproducible      | Base ya implementada                          | `npm ci`, lockfile, `.nvmrc`, build limpio y CI ya lo garantizan. Falta política de artefactos de release/provenance antes de publicar en npm (fase 5).                                                                                                    |
| GitHub Actions          | Base ya implementada                          | CI cubre instalación limpia, verificación completa y auditoría de producción en Node 22/24. Falta escaneo de secretos en el historial y política de releases antes de hacer público el repositorio (fase 6).                                               |
